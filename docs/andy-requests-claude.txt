4. Claude Session Viewer —— 在 Zed 裡用「網頁版的顯示品質」看／控制正在跑的 Claude Code session

================================================================================
0. 動機與目標
================================================================================

現況：Claude Code 跑在 tmux 裡，用 `--remote-control` 讓手機／網頁可以遠端控制。
Terminal 只能顯示純文字 + ANSI 顏色，沒有圖片、沒有精緻表格、tool call 無法折疊、
subagent 在做什麼完全看不到。但網頁與手機 app 顯示得很好。

目標：在 Zed 開一個 panel，接上「已經在跑的」那個 Claude session，用 Zed 既有的
markdown / diff / image render 能力顯示，並且能送輸入。tmux、手機、網頁、Zed 四邊
看到的是同一個 session。

非目標（明確排除）：
  - 不嵌 webview（GPUI 沒有 webview，gpui/gpui_macos 內 `WKWebView` 零命中）。
  - 不逆向 remote-control bridge 的網路協定。
  - 不取代 Zed 既有的 Agent Panel（那是 Zed 自己起的 ACP session，與本功能無關）。

--------------------------------------------------------------------------------
0.1 為什麼可行（已實測）
--------------------------------------------------------------------------------

Claude Code CLI 把完整結構化對話寫在本機檔案，不管輸入來自 terminal、手機還是網頁，
都是同一個 process 寫同一份檔。所以只要讀檔就能拿到 100% 的內容，包含 image block、
thinking block、結構化 tool result。

本文件所有欄位名稱都是在 2026-09-10 於 Claude Code 2.1.263 / 2.1.266 / 2.1.267 的
實機資料上驗證過的，不是推測。


================================================================================
1. 資料來源（實測）
================================================================================

--------------------------------------------------------------------------------
1.1 Session 註冊表 —— ~/.claude/sessions/<pid>.json
--------------------------------------------------------------------------------

每個活著的 claude process 一個檔。這是列舉與追蹤的唯一權威來源。

實例（原文照抄）：

    {
      "pid": 10064,
      "sessionId": "4e2e3600-89c0-4cd5-9994-525c708559ab",
      "cwd": "/Users/andy/go/src/github.com/poi5305/zed",
      "startedAt": 1789007244364,
      "procStart": "Thu Sep 10 02:27:23 2026",
      "version": "2.1.267",
      "peerProtocol": 1,
      "peerFeatures": ["notify_idle", "reply_across_default_dirs", "artifact_yield"],
      "kind": "interactive",
      "entrypoint": "cli",
      "pidDomain": "darwin",
      "tmux": "zed:@6.%8",
      "messagingSocketPath": "/tmp/cc-socks/10064.sock",
      "name": "zed-e4",
      "nameSource": "derived",
      "nameSince": 1789007244364,
      "status": "busy",
      "updatedAt": 1789009278063,
      "statusUpdatedAt": 1789009278063,
      "bridgeSessionId": "session_01Tf2BzmxZDH3YKYpdxtSrpD"
    }

我們用到的欄位：
  sessionId            → transcript 檔名。**權威來源，不是檔案系統掃描。**
  cwd                  → 用來過濾「跟目前 Zed project 相關」的 session。
  tmux                 → "<session_name>:<window_id>.<pane_id>"，直接可當 send-keys target。
                         **可能不存在**（非 tmux 內啟動的 session，例如被 spawn 的子 session）。
  pid + procStart      → 判活。兩者都要比對，procStart 用來防 pid 重用。
  status / statusUpdatedAt → "busy" / 其他；做 UI 上的忙碌指示。
  updatedAt            → heartbeat；太舊視為 stale。
  version              → 顯示用，也用來對未知格式做降級。
  kind                 → "interactive"；非 interactive 的不列。
  name                 → 顯示名稱（例：zed-e4）。
  messagingSocketPath  → 見 §6.2，第一版不使用。
  bridgeSessionId      → 有值代表這個 session 正被 remote-control 接管；UI 上標一個 icon。

旁邊還有 `~/.claude/sessions/<pid>.<sha256>.key`（108 bytes）。
**視為機密，不得讀取、不得記錄、不得傳輸。** 與 messagingSocketPath 成對，
是 §6.2 那條未採用的通道的憑證。

註冊檔是 stale 的（實機上看到好幾天前的殘留），一定要判活。

--------------------------------------------------------------------------------
1.2 主 transcript —— ~/.claude/projects/<slug>/<sessionId>.jsonl
--------------------------------------------------------------------------------

JSON Lines，append-only。

**不要自己算 <slug>。** 看起來是把 cwd 的 `/` 換成 `-`，但這是未文件化的規則。
一律用 glob 定位：

    ~/.claude/projects/*/<sessionId>.jsonl

已知的 top-level `type` 值（實測列舉，非窮舉）：

    user                對話中的 user 訊息，或 tool_result 回填
    assistant           assistant 訊息
    attachment          系統注入的上下文（見 §1.5）
    system              系統事件，用 `subtype` 再分（見下）
    file-history-snapshot
    mode / permission-mode / bridge-session / atis-latch
    last-prompt / ai-title / queue-operation

已知的 system `subtype`：

    compact_boundary    壓縮分界（見 §3.2）—— 必須處理
    bridge_status       remote-control 狀態變化
    local_command       本機 slash command 的 stdout（含 ANSI escape）
    away_summary / turn_duration

`message.content` 內的 block type：`text` / `thinking` / `tool_use` / `tool_result` / `image`。

每筆記錄的通用欄位：

    uuid                本筆 id
    parentUuid          前一筆的 uuid，**null 代表這是一個 root**
    isSidechain         true 代表這筆屬於 subagent（在主檔內為 false；見 §4）
    timestamp / sessionId / cwd / gitBranch / version
    toolUseResult       tool 的**結構化**結果（例：{stdout: ...}）。
                        比 content block 裡的文字更豐富，rich render 主要靠這個。
    isMeta / userType / requestId / promptId / effort / perTurnEffort

--------------------------------------------------------------------------------
1.3 Subagent transcript —— <sessionId>/subagents/agent-<agentId>.{jsonl,meta.json}
--------------------------------------------------------------------------------

meta.json（原文照抄）：

    {
      "agentType": "general-purpose",
      "description": "WP1 forward ports WSL/Docker",
      "toolUseId": "toolu_01Qv7iieSWkvLp17oyUTbodG",
      "spawnDepth": 1,
      "requestShape": "background",
      "requestNonInteractive": true,
      "model": "opus"
    }

  toolUseId   → 對應主 transcript 裡那個 `tool_use` block 的 `id`。
                **這是 subagent 掛回主對話正確位置的唯一連結。**
  spawnDepth  → 巢狀層數，支援 subagent 再開 subagent。
  agentType / description / model / requestShape → 卡片上的顯示資訊。

agent-<agentId>.jsonl 與主檔同格式，差別：
  - 每筆都有 `isSidechain: true` 與 `agentId`
  - 自己的 parentUuid 鏈，root 的 parentUuid 為 null
  - 另有 `attributionAgent`

**這些檔在 subagent 執行期間就持續在寫**（實測：跑到一半的 agent 檔已 689KB 且 mtime
持續更新）。所以「即時看 agent 在做什麼」不需要任何額外機制，tail 這個檔就是了。

完成訊號：主 transcript 出現對應 `toolUseId` 的 `tool_result`。

--------------------------------------------------------------------------------
1.4 卸載的大型輸出 —— <sessionId>/tool-results/
--------------------------------------------------------------------------------

超過門檻的 tool 輸出不會寫進 transcript，而是存成獨立檔，transcript 裡放：

    <persisted-output>
    Output too large (30.2KB). Full output saved to: <絕對路徑>
    Preview (first 2KB):
    ...

檔名兩種：`<9碼隨機>.txt`（tool 輸出）、`hook-<uuid>-stdout.txt`（hook 輸出）。

**這是 Zed 版明顯勝過 terminal 的地方**：terminal 只看得到 2KB preview，
Zed 可以在展開時 lazy load 整個檔。要 parse 那個 marker 把路徑抓出來。

--------------------------------------------------------------------------------
1.5 Attachment
--------------------------------------------------------------------------------

`type: "attachment"` 的記錄帶 `attachment.type`，實測值：

    environment / model / deferred_tools_delta / mcp_instructions_delta
    hook_success / invoked_skills / prompt_snapshot / queued_command
    compact_file_reference / edited_text_file / file / opened_file_in_ide
    selected_lines_in_ide / total_tokens_reminder / agent_listing_delta

多數是雜訊，預設全部收在一個可展開的「context」摺疊區，不要平鋪在對話流裡。


================================================================================
2. Session 探索與列舉
================================================================================

流程：

  1. 列 `~/.claude/sessions/*.json`，逐檔 parse（單檔壞掉就跳過該檔，不要整批失敗）。
  2. 判活：pid 存在 **且** `procStart` 相符 **且** `updatedAt` 在合理範圍內。
  3. 過濾 `kind == "interactive"`。
  4. 用 glob `~/.claude/projects/*/<sessionId>.jsonl` 定位 transcript；找不到就標成
     "no transcript" 而不是丟掉（session 可能剛啟動）。
  5. 依 `cwd` 是否落在目前 Zed project 的 worktree 內，分成「本專案」與「其他」兩組。

**三個實測出來的坑，一定要照做：**

  (a) 不要用 tmux 掃描來偵測 claude。`pane_current_command` 實測顯示的是版本號
      （`2.1.267`），因為 argv[0] 指到 `~/.local/share/claude/versions/<ver>`，
      不是 `claude`。反過來要從註冊表的 `tmux` 欄位去對應 pane。

  (b) 不要讀別的 process 的環境變數。macOS 下 `ps eww -p <其他 pid>` 回空
      （SIP／hardened runtime）；Linux 的 `/proc/<pid>/environ` 才可行。
      不要寫成只在 Linux 能動的邏輯。

  (c) 不要自己組 project slug 路徑，用 glob。


================================================================================
3. Transcript 模型 —— 這一節做錯會從根上歪
================================================================================

--------------------------------------------------------------------------------
3.1 它是一棵樹，不是平坦 log
--------------------------------------------------------------------------------

每筆有 `uuid` + `parentUuid`。檔案是 append-only，但**對話內容是從 leaf 沿
parentUuid 往回走的那條路徑**，不是檔案的行序。

rewind（Esc Esc）、`--resume` 分支、compact 都會在同一個檔裡留下已被拋棄的分支。
線性播放會把死掉的分支畫出來。

正確做法：
  - 維護 `uuid -> record` 的 map，以及目前的 leaf。
  - 增量 tail 拿到新 record → 塞進 map、更新 leaf、重算 path。
  - 正常情況 path 只在尾端 append，diff 極小；只有 rewind 才整段換掉。

--------------------------------------------------------------------------------
3.2 /compact —— 實測結論（在 33 筆歷史 compact 上驗證）
--------------------------------------------------------------------------------

**compact 不換檔、不換 sessionId。**（掃過全部 294 個歷史 transcript，
sessionId 與檔名不符的案例：0。）

它在同一個檔裡寫入一筆：

    {
      "type": "system",
      "subtype": "compact_boundary",
      "parentUuid": null,                                   ← 鏈條被刻意切斷
      "logicalParentUuid": "0be38277-...",                  ← 指回壓縮前的 leaf
      "content": "Conversation compacted",
      "level": "info",
      "compactMetadata": {
        "trigger": "manual",
        "preTokens": 792090,
        "postTokens": 16995,
        "cumulativeDroppedTokens": 775095,
        "durationMs": 133856,
        "preservedSegment": { "headUuid": "...", "anchorUuid": "...", "tailUuid": "..." },
        "preservedMessages": { "anchorUuid": "...", "uuids": [...], "allUuids": [...] }
      }
    }

緊接著是一筆 `user` 記錄，帶 `isCompactSummary: true`，內容是
"This session is being continued from a previous conversation..." 的摘要。

推論出的規則：
  - N 次 compact → 檔案裡有 N+1 個 root（實測：boundaries=5 的檔有 6 個 root）。
  - 從 leaf 往回走會停在最近一個 compact_boundary，這正是「模型現在看得到的
    上下文」。
  - 要顯示完整歷史，就在 boundary 處改跟 `logicalParentUuid` 繼續往回走。

UI 要求：
  - 在 boundary 處畫一條明確的分界，顯示 `trigger` 與 `preTokens -> postTokens`。
  - 分界以上的歷史**預設折疊**，可展開（這是 terminal 做不到、網頁版也不見得有的優勢）。
  - `isCompactSummary: true` 那筆要標成「摘要」樣式，不要當成使用者真的打了這段字。
  - `trigger` 實測只出現過 `"manual"`；對其他值（很可能有 `"auto"`）要容錯，
    未知值就原樣顯示。

--------------------------------------------------------------------------------
3.3 /clear 與 resume
--------------------------------------------------------------------------------

`/clear` 換 sessionId → 換一個新的 transcript 檔，pid 不變。

所以：**主要監看對象是 `~/.claude/sessions/<pid>.json`，不是 transcript 檔。**
sessionId 一變就切檔、清畫面、重建 map。只 watch transcript 的話，clear 之後
Zed 會永遠停在舊對話。

舊檔不會被截斷或改寫，所以 byte offset 不會錯亂。但仍要做 sanity check：
檔案 size < 已記錄的 offset → 從頭重讀。


================================================================================
4. Subagent / Workflow 檢視
================================================================================

這是本功能相對網頁版與 terminal 的**主要價值**：同時看多個 agent 在做什麼。

--------------------------------------------------------------------------------
4.1 資料串接
--------------------------------------------------------------------------------

  1. 主 transcript 出現 `tool_use`，name 為 `Agent`（或其他會 spawn 的 tool）。
  2. 掃 `<sessionId>/subagents/*.meta.json`，用 `toolUseId` 對回那個 block 的 `id`。
  3. 對上了就在主對話的那個位置掛一張可展開的 agent 卡片。
  4. 展開 → tail `agent-<agentId>.jsonl`，用跟主 transcript 完全相同的 render pipeline。
  5. `spawnDepth > 1` → 巢狀顯示。

狀態判定：
  running  = 主 transcript 尚無對應 toolUseId 的 tool_result
  done     = tool_result 已出現
  進度提示  = agent jsonl 的最後一筆 record（最近一次 tool_use 的名稱／目標）+ mtime

主 transcript 另有 `pendingBackgroundAgentCount` 欄位，可直接當 header 上的計數徽章。

--------------------------------------------------------------------------------
4.2 UI：agent 切換
--------------------------------------------------------------------------------

Panel 頂端一列 tab／chip：

    [ Main ]  [ WP1 forward ports WSL/Docker ●]  [ WP3 project_manager fixes ●]  ...

  - 標籤文字用 meta 的 `description`；hover 顯示 `agentType` / `model` / `spawnDepth`。
  - `●` 表示還在跑（用 mtime + 有無 tool_result 判定）。
  - 點一下把主檢視切到那個 agent 的 transcript；Main 切回主對話。
  - 主對話裡對應位置的 agent 卡片也可以就地展開（inline），兩種入口都要有。
  - agent 已結束的仍要留在列上（灰掉），才能事後回看。
  - 這是**唯讀**檢視。不提供對 subagent 直接輸入。

Workflow 的 `agent()` 產出同樣落在 `subagents/`（meta 帶 `model` 欄位），
所以不需要為 Workflow 另做一套；同一個機制涵蓋。


================================================================================
5. UI 與 render
================================================================================

  - 落點：新的 dock panel，或 workspace item（tab）。**不要動 Zed 既有的 Agent Panel。**
  - 對話流用 Zed 既有的 markdown render；`ContentBlock::Image` 在
    crates/acp_thread/src/acp_thread.rs:1746 已經支援圖片，沿用同一條路徑。
  - `thinking` block：預設折疊。
  - `tool_use` / `tool_result`：折疊卡片。優先用 top-level `toolUseResult`（結構化）
    而不是文字 content block 來做 rich render（diff、檔案內容、命令輸出）。
  - `<persisted-output>` marker：顯示 preview，加一個「載入完整輸出」按鈕（§1.4）。
  - attachment：全部收進一個折疊的 context 區。
  - `local_command` 的 content 含 ANSI escape，要先 strip 或轉成樣式。
  - Header：session name、cwd、version、status、bridge 圖示、tmux target、pending agent 數。
  - 未知的 record type / block type / attachment type → **降級成 raw JSON 摺疊區顯示，
    絕對不要丟棄、不要 panic**。格式是私有的，一定會變。

6. 輸入通道
================================================================================

--------------------------------------------------------------------------------
6.1 第一版：tmux send-keys
--------------------------------------------------------------------------------

target 直接來自註冊表的 `tmux` 欄位（例：`zed:@6.%8`），不需要自己找 pane。

要處理：
  - 多行輸入的送法（bracketed paste）。
  - Esc 中斷。
  - 註冊表沒有 `tmux` 欄位的 session → 輸入框停用，只提供唯讀檢視。

--------------------------------------------------------------------------------
6.2 未採用：本機 IPC socket
--------------------------------------------------------------------------------

`messagingSocketPath` (`/tmp/cc-socks/<pid>.sock`) 加上 `~/.claude/sessions/<pid>.<sha>.key`
看起來是一條乾淨的本機 IPC。完全未文件化，協定不明。

**第一版不碰。** 記錄在此供日後評估。key 檔內容任何情況下都不得寫入 log。


================================================================================
7. Remote 支援
================================================================================

架構上沒有新東西：全部是「讀遠端檔案 + 遠端 tmux」。沿用既有的
crates/proto/proto/tmux.proto 那條路。

需要新增：

  - RPC：列出遠端的 claude sessions。在 remote_server 上讀 `~/.claude/sessions/*.json`、
    判活、glob transcript 路徑，回傳**結構化結果**。
    不要把 raw JSON 丟給 client 解 —— 遠端的 Claude Code 版本可能與本機不同，
    格式的相容性處理要留在產生端。

  - RPC：tail transcript。輸入 `(path, offset)`，回傳新增的 bytes 與新的 offset。
    同一支 RPC 也要能 tail subagent jsonl 與讀 tool-results 檔。

  - **第一版用輪詢（約 1 秒），不要做 remote file watch。**
    這些檔在 worktree 之外，走不到既有的 worktree scanner；而輪詢一個 append-only
    檔的成本可以忽略，省掉一整套遠端 watch 的生命週期問題。

  - `~` 必須在遠端 resolve，不能用本機 home。

Client 端抽一個 source trait（list / tail / read_blob 三個方法），
local 直接讀檔、remote 走 proto，UI 層完全不分本地遠端。


================================================================================
8. 風險
================================================================================

  - 這些檔案格式全是私有且未文件化的，會隨版本變。
    緩解：唯讀為主；未知欄位一律降級顯示；註冊表的 `version` 欄位可用來做提示。
    最壞情況是某段 render 不漂亮，不會弄壞任何 session。

  - `.key` 檔與 `messagingSocketPath` 屬敏感資訊，不讀、不記、不傳。

  - transcript 可能很大（實測單檔 2.7MB / 2695 筆），且 subagent 檔在跑的時候
    分分鐘幾百 KB。要做增量 parse 與虛擬捲動，不要整檔重 parse 重 render。

  - 註冊表有 stale 殘留，判活不能只看檔案存在。


================================================================================
9. 分期
================================================================================

  P1  本機唯讀：session 列舉 + 主 transcript rich render + compact/clear 正確處理。
      這一段本身就有價值，且完全無副作用。

  P2  Subagent / workflow 檢視與切換（§4）。

  P3  輸入（tmux send-keys）。

  P4  Remote（§7）。

P1 有兩條必須一開始就做對，其餘都能事後補：
  (1) 跟註冊表 `<pid>.json` 的 sessionId 走，不跟 transcript 檔名走。
  (2) 從 leaf 沿 parentUuid 走，遇 compact_boundary 用 logicalParentUuid 續接，
      不做線性播放。

A.0 共通規則（每一份派工 prompt 都要帶）
--------------------------------------------------------------------------------

B.1 修訂（對應 F9）：persisted output 的辨識改用結構化欄位
--------------------------------------------------------------------------------

**問題**：正文 §1.4 說用 `<persisted-output>` marker 文字去認卸載的大型輸出。
但實作出來之後，整條路徑在生產環境是死碼——因為 `toolUseResult`（結構化）
勝過 content block，而 `toolUseResult.stdout` 裡沒有 marker。

**實測資料（2026-09-10，掃全部歷史 transcript）**

    toolUseResult 帶 persisted* 欄位的記錄：86 筆
      persistedOutputPath：85 筆
      persistedOutputSize：85 筆
    tool_result block 的 content 含 <persisted-output> marker：86 筆
    樣本：
      persistedOutputPath = ".../tool-results/b7vd9w357.txt"
      persistedOutputSize = 82585
      stdout 長度         = 29999   ← 被截在 30000，**不含 marker**
      resultKeys = [stdout, stderr, interrupted, isImage,
                    noOutputExpected, persistedOutputPath, persistedOutputSize]

**裁決：不是二選一，兩個都要。** review 輪提的 (a) 保留 stdout 內嵌、
(b) 改用 marker preview 加載入按鈕——兩者都比正確答案差：

  - 內嵌本文用 `toolUseResult.stdout`（實測 30 KB），**不是** marker 的 2 KB preview。
    這是使用者立刻看到的東西，30 KB 遠勝 2 KB，也遠勝 terminal。
  - **同時**，當 `persistedOutputPath` 存在時，顯示「Load full output」按鈕，
    大小標示用 `persistedOutputSize`（實測 82,585），按下才讀那個路徑。
  - 也就是說「內嵌 preview」與「可載入完整」是兩件獨立的事，不互斥。
    原規格把它們綁在一起才產生了死碼。

**路徑淨化（F3 已修的那條，這裡再收緊一次）**

  - 路徑**只能**來自 `toolUseResult.persistedOutputPath`，或
    `type == "attachment"` 記錄的 marker 文字（hook 輸出走這條）。
  - **絕對不得**從 `message.content` 的文字（user text、assistant text）解析路徑。
    實測 marker 從不出現在那裡，任何在那裡的 marker 都是偽造或巧合。
  - 讀檔前必須驗證：路徑是絕對路徑，且位於
    `<home>/.claude/projects/` 之下。不符就不顯示按鈕（顯示原文即可），
    不要顯示一個會失敗的按鈕。
  - marker 文字解析保留為 fallback（85/86 有結構化欄位，那 1 筆與 attachment 需要它）。

B.2 修訂（對應 F11）：visible_sessions 的排序平手規則
--------------------------------------------------------------------------------

**問題**：正文 §2 與附錄 A.2 定義排序 key 為
`(是否屬於本專案 == false, name 字串序)`，沒有定義平手時怎麼排。
於是同名（或同為 None）的 session 繼承 `read_dir` 的任意順序，
每次輪詢都可能互換，UI 列會閃動。

**裁決：加第三段 tiebreaker `process_id` 遞增。**

    排序 key = (是否屬於本專案 == false, name 字串序, process_id 遞增)

理由：`process_id` 在活著的 session 之間唯一、在 session 生命期內不變、
是數值比較不需要正規化。`session_id` 也唯一但沒有比 pid 更好的性質。

`name` 為 `None` 時排序仍當空字串（原規則不變）。

B.3 修訂（對應 F8）：對話 entry 要以 record uuid 為鍵快取
--------------------------------------------------------------------------------

**問題**：正文 §5 與附錄 A.5 只寫了「必須虛擬捲動」「切換 session 時不得整份重
parse」，沒有寫「同一個 session 收到新資料時不得整份重建」。
於是實作每次 store 通知都在前景執行緒走完整條 path 重建所有 entry：
每張圖重新 base64 解碼（貼上的截圖每張約 1.5 MB）、每筆 unknown 記錄重新
pretty-print JSON，然後再逐位元組比較找出差異。串流中每秒最多 4 次。

**裁決：規格補一條——昂貴的 per-record 產物必須以 record uuid 為鍵快取，
跨重建存活。**

  - 快取鍵：`record uuid`（+ block index，因為一筆記錄可以有多個 block）。
  - 必須跨重建存活的產物：base64 解碼後的圖片位元組、pretty-print 的 raw JSON、
    ANSI strip 後的文字、markdown 來源字串。
  - 記錄一旦吸收就不會再變（append-only + uuid 覆蓋是罕例），
    所以快取不需要失效策略；只需要在切 session／transcript restart 時整份丟棄。
  - 同 uuid 被覆蓋（`absorb` 允許）時要丟該鍵的快取。
  - 這條**不是**效能優化的建議，是正確性層級的要求：
    沒有它，本功能在它最該發光的場景（長 session、貼了截圖）會卡。

--------------------------------------------------------------------------------
D.1 `procStart` 是 UTC，`ps -o lstart=` 是本地時區
--------------------------------------------------------------------------------

正文 §2 與 A.2 事實清單只寫「與註冊檔的 `procStart` 做字串比對」，
沒有寫時區。實機量到：

  registry procStart : Thu Sep 10 02:53:02 2026
  ps -o lstart=      : Thu Sep 10 10:53:02 2026     ← 本地 (Asia/Taipei, +8)
  TZ=UTC ps -o lstart=: Thu Sep 10 02:53:02 2026    ← 相符

7 個註冊檔（CLI 版本 2.1.257 ~ 2.1.267）全部相差正好 8 小時，
即 Claude Code 寫入的是 UTC 呈現。字串比對永遠不相等 →
每一個 session 都被判 `PidReused` → 全部被 `visible_sessions` 濾掉。

**修訂**：取 process start time 的指令必須固定在 UTC 執行
（`command.env("TZ", "UTC")`）。回歸測試
`test_process_start_times_are_reported_in_utc`：spawn 一個真的 process、
把回傳字串以 UTC 解析成 epoch、與 spawn 當下的時間比對，容差 5 秒。
修之前紅在 `off by 28800 seconds`。

  註：這支測試不能用 `#[gpui::test]`——await 真的 `ps` 會踩到
  GPUI deterministic scheduler 的 "Parking forbidden"。改成一般
  `#[test]` + `smol::block_on`。

--------------------------------------------------------------------------------
D.2 `updatedAt` 不是 heartbeat，不得當判活條件
--------------------------------------------------------------------------------

正文 §1.1 寫「`updatedAt` → heartbeat；太舊視為 stale」，§2 判活第 2 條
要求「`updatedAt` 在合理範圍內」，A.2 據此定 `STALE_HEARTBEAT_MILLIS = 60_000`。
實機 7 個註冊檔**每一個** `updatedAt == statusUpdatedAt`，也就是它只在
session 狀態改變時被改寫，不是定時心跳：

  web-tools-16    status=idle   updatedAt 距今 3336s   process 活著
  dashboard-0f    status=busy   updatedAt 距今  284s   process 活著
  phoneoncloud-81 status=idle   updatedAt 距今 138842s process 活著

等在使用者輸入前的 idle session、或卡在一個長 tool call 的 busy session，
都會好幾小時不動 `updatedAt`。所以 60 秒門檻即使在 D.1 修好之後，
仍然只會留下「剛剛改過狀態」的那一個 session。

**修訂**：判活只看 process 本身（pid 存在 **且** `procStart` 相符）。
`updatedAt` 只能拿來顯示，不得作為隱藏 session 的依據。
實作上 `liveness()` 的 API 與既有測試（含盲測）都不動——門檻由呼叫端給，
`session_store` 改傳 `HEARTBEAT_CUTOFF_MILLIS = i64::MAX`。
回歸測試 `test_a_session_that_has_not_changed_status_for_an_hour_is_still_listed`。

  `Liveness::StaleHeartbeat` 這個 variant 因此在 production 走不到。
  保留它是因為 `liveness()` 是純函式、門檻是參數，變體本身沒有錯；
  錯的是正文對 `updatedAt` 語意的假設。

E.8 驗收發現：tail RPC 的任意檔案讀取（已修）

WP7 交付後我驗 diff 發現的洞，嚴重度足以當場修，不留到 Wave 4。

`read_transcript_tail(home, session_id, state)` 的語意是「`state.path` 存在就照著讀，
否則才 glob」。這在 local 沒問題（path 是自己上一輪 glob 出來的），
但 `TailClaudeTranscript.path` 是 **client 傳來的**，於是 handler 會照著讀任何
remote server 讀得到的檔案。取證（暫時測試，跑完已還原）：

  tail returned lines ["sk-secret-value-that-must-never-be-read"]
    from Some("/var/folders/.../probe-not-a-transcript.key")

也就是 `~/.claude/sessions/<pid>.<sha>.key` 可以被這條路徑讀出來 ——
正文 §1.1／§8 明文「不讀、不記、不傳」的那個檔。

**修法**（在 server 端信任邊界，`headless_project.rs`）：
新增純函式 `transcript_path_to_follow(path, session_id, home)`，client 傳來的 path
必須同時滿足：絕對路徑、位於 `<home>/.claude/projects/` 之下、不含 `..` component、
檔名正好是 `<session_id>.jsonl`。不符就當成 `None`（不是回錯），
讓 server 用 session_id 自己重新 glob —— 語意上正好等於「你追的檔不見了，重找」。

**三個 clause 各自有一個只有它抓得到的案例，逐一突變都會變紅**：

  拿掉 `starts_with(projects)`  → `<home>/.claude/sessions/<session>.jsonl` 這案變紅
  拿掉檔名檢查                 → `projects/x/another-session.jsonl` 這案變紅
  拿掉 `..` 檢查               → `projects/x/../../.claude/sessions/<session>.jsonl` 這案變紅

**「什麼合法輸入會被誤殺」**：拿本機真的 7 個 session 跑 production 路徑
（`list_sessions` → `transcript_path_to_follow`），6 個有 transcript 的全部通過，
第 7 個本來就沒有 transcript（SDK session）。誤殺 0 筆。

  註：`paths::home_dir()` 在 `cfg(test)` / `feature = "test-support"` 下固定回
  `/Users/zed`（見 crates/util/src/paths.rs:27），所以測試裡拿不到真的 home，

E.9 WP6 回報的五個規格問題 —— 大腦裁定
--------------------------------------------------------------------------------

1. **「送出成功後清空輸入框」字面上做不到，且照字面做會更糟。**
   WP6 指出：等 tmux 三個子指令跑完（數十毫秒）才清空，會把使用者這段期間
   新打的字一起吃掉。它的實作是交付給 source 的當下就清空。
   **裁定：清空時機維持不變（交付即清），但送出失敗必須把文字還回輸入框，
   且只在輸入框當下仍為空時才還**（使用者又打了字就不准蓋掉）。
   這條列進 WP9 施工，附三支測試（失敗且空→還回、失敗但已有新內容→不覆蓋、成功→保持空）。

2. **`error` 加來源標記（`ErrorSource::Poll` / `Send`）：接受。**
   這不是超出最小差異，是修一個真 bug —— 原本 `apply_registry_scan` 每次成功掃描
   都 `self.error.take()`，1 秒的輪詢會在使用者讀到之前把送出失敗的訊息清掉。
   測試會綠只是因為測試控制時鐘。顯示位置與機制沒換，保留。

3. **空白訊息被擋掉：接受。**
   誤殺的合法輸入是「只按 Enter」—— 在 Claude Code 裡那等於接受權限提示的
   預設選項。擋掉是對的：輸入框有焦點時誤按 Enter 會直接授權一個可能破壞性的工具。
   使用者要接受提示仍可打「1」再 Enter，或按 Esc 中斷。
   若日後要支援，應該做成明確的「Approve」按鈕，不是讓空訊息穿過去。

4. **三支 registry 測試改了呼叫方式：接受，我逐字比對過。**
   斷言文字的雜湊在兩支上完全相同；第三支
   （`test_registry_scan_normalizes_padded_process_start`）唯一差別是
   `session.process_start` 變成 `summary.session.process_start`，語意不變。
   WP6 說「padded 那支現在有一半在驗測試 helper」是對的，但它仍然釘住
   store 的列舉路徑吃 padded procStart 會判 Live；等價的產品路徑覆蓋在
   `remote` 自己的 `test_list_sessions_reports_sessions_with_and_without_a_transcript`
   與 `test_normalize_whitespace_matches_padded_ps_output`。兩邊都留。

5. **`transcript_path()` 最多落後一次 registry 輪詢（1 秒）：接受。**
   「還沒有 transcript」與「transcript 是空的」兩句提示的切換慢一拍，不是 bug。

這批 P3/P4 的程式碼主要是 Opus 寫的，所以安全面交給不同家族審（CLAUDE.md 要求）。
唯讀、只找不修、只准輸出 JSON。它審五個界限，回報 A/C/E 乾淨、兩條 finding：

**S1（high）—— `validate_claude_file_path` 界限過寬。根因是我 spec 寫錯。**

  它允許整個 `<home>/.claude/`，於是 client 可以用 `proto::ReadClaudeFile` 讀走
  `<home>/.claude/sessions/<pid>.<sha256>.key` —— 正文 §1.1／§8 明文
  「不讀、不記、不傳」的那個檔。

  這條界限是我在 E.4 的派工裡寫成「必須落在 `<home>/.claude/` 之下」的，
  WP7 照做沒有錯。實際上被 offload 的 tool 輸出只住在
  `<home>/.claude/projects/<slug>/tool-results/*.txt`，而 client 端同一條界限
  （`persisted_output_is_loadable`）用的就是 `home/.claude/projects` ——
  兩邊本來就不一致，寬的那邊在 server。

  這正是「安全／金流／刪除加第二輪、換不同家族」這條規則要抓的東西：
  同家族審同家族不會有人去質疑派工裡那行界限。

**S2（medium）—— `send_text` 沒有失敗／取消的清理。**

  `load-buffer` 成功之後若 `paste-buffer` 失敗（pane 不存在）或 Task 被 drop，
  那個 buffer 會留在 tmux server 的 buffer stack 頂端，使用者手動貼上
  （prefix + `]`）會意外貼出剛才那段文字。若 drop 發生在 paste 之後、
  `send-keys Enter` 之前，文字會留在終端機裡沒送出。

兩條都交給 Wave 4 的 Opus review 那一輪獨立驗證、寫 RED 測試、修到綠
（來源標 handed，誤報要標 rejected 並說明理由）。

E.13 R2 從 wontfix 改成修（大腦解除了它的阻礙）
--------------------------------------------------------------------------------

review 輪把 R2（兩個併發 send 的三個 tmux 行程會交錯，導致兩則訊息被併成一則、
再送一個空行）標成 wontfix，理由是「要驗證得對真 pane 送輸入，這輪禁止」。

那個阻礙是我的規則造成的，所以我自己去驗：開一個拋棄式 tmux session
（`cat >> /tmp/probe.out`），實測**一次呼叫**的 command list 可行：

  printf 'line one\nline two' | tmux load-buffer -b probe1 - ';' \
    paste-buffer -d -p -b probe1 -t %11 ';' send-keys -t %11 Enter
  → exit 0、檔案收到 "line one\nline two\n"（多行保留、Enter 送出）、buffer 不殘留

tmux server 是單執行緒事件迴圈、逐個處理一個 client 的 command list，
所以一次呼叫就沒有中間可被別的 send 插進來的空隙。已派工改成這個形式，
並要求：失敗清理照舊保留（load-buffer 成功後 paste 失敗時 buffer 仍會留下）、
`send_escape` 不動、端到端驗證只能用拋棄式 session、收工不得留下 session 或 buffer。

**規格補充（R1 交回的規格漏洞，一併定案）**：
`sessionId` 一律視為不可信輸入 —— 它只能構成**單一 path component**，
client、server、local 三邊用同一條規則。

E.14 R2 修完 + 大腦把 opt-in 測試改成預設跑
--------------------------------------------------------------------------------

`send_text` 收成**一次** tmux 呼叫：

  load-buffer -b <name> - ";" paste-buffer -d -p -b <name> -t <pane> ";" send-keys -t <pane> Enter

`";"` 是獨立的 argv 元素，不經 shell；文字仍然只走 stdin。抽出純函式
`send_text_arguments(buffer_name, pane_target)` 釘住「單一 argv、兩個 `;`、順序正確」——
併發競爭本身無法穩定重現，所以釘的是結構性質：任何人把它拆回三個呼叫就會紅。
失敗清理（`delete-buffer`）保留，因為 command list 裡 paste 失敗時 load 已經成功、buffer 會留下。
`send_escape` 未動。

**大腦補的一件事**：它把端到端那支（真的開一個 `cat` session、送兩行、讀檔驗內容）
設成環境變數 opt-in，理由是會跟既有的
`a_send_that_cannot_reach_its_pane_leaves_no_paste_buffer_behind` 互踩
（後者斷言「此 process 沒有 `zed-claude-<pid>-` 前綴的 buffer」，前者會短暫持有一個）。
它不准改既有測試，所以只能 opt-in —— 代價是那支不在預設路徑上，等於 CI 不跑。

我把根因解掉：`mod tests` 加一個 `TMUX_SERVER_TESTS: Mutex<()>`，兩支都先取鎖
（poison 用 `into_inner()` 跨過，免得一支失敗連帶讓另一支噴出誤導的第二個失敗），
然後移除環境變數 gate。既有測試只多一行取鎖，**斷言一字未改**。

  連跑三次 `cargo test -p remote` → 96 passed / 0 failed，無 flake。
  非空測證明：把 command list 最後的 `Enter` 改成 `Space`
    → `a_multi_line_send_arrives_in_the_pane_as_one_message` 紅在
      left: "line one\n" / right: "line one\nline two\n"。
  收工時 tmux 沒有 `zed-claude-*` session 或 buffer 殘留。

它自己列的殘留風險，我的處置：
  - 「兩則訊息的先後順序」不保證（panel 兩個 detach task 誰先跑到 tmux 誰先送）：
    接受。使用者連按兩次 Enter 的兩則訊息都會完整送到，只是順序可能互換，
    不會被併成一則，也不會misroute 到別的 session。
  - 「錯誤訊息變粗」（整串 command list + tmux stderr）：接受，仍看得到 tmux 的原因。
  - 「依賴 tmux 對 `;` 的語意」：本機 3.6b 實測成功與失敗路徑都符合；
    很舊的 tmux 會退化成什麼，純函式測試抓不到，只有端到端那支抓得到 ——
    而它現在預設會跑。
